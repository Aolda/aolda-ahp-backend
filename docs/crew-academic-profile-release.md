# Crew 학번 표시 수정

## 동작

- `NOTION_TEAM_DB_IDS`의 기존 `crew_profile` 데이터 소스를 Crew 동기화에서 함께 읽는다. 별도의 비밀값은 추가하지 않는다.
- `사용자계정`으로 먼저 연결하고, 계정이 충돌하지 않는 경우에만 고유 이메일을 보조 키로 사용한다. 이름만으로 연결하거나 중복 프로필 중 하나를 임의 선택하지 않는다.
- 프로필의 `학과`와 `학번`을 수집한다. 9자리 학번은 앞 4자리 입학연도만 저장/응답한다. 2자리·4자리 연도도 지원한다. `00`/`0000`은 미등록이며, 명시적인 `2000`은 유효하다.
- 관리자 수정값 > Notion 수집값 > 빈 값 순으로 목록·상세·프로젝트 참여자 응답에 적용한다. 프런트엔드는 빈 값에 `학번 미등록`을 표시한다.
- 관리자 콘솔에서 학과/입학연도 수정값을 비우면 Notion 값으로 돌아간다. 일반 프로필 수정에서 해당 필드를 생략하면 기존 수정값을 유지한다.
- 미설정·미매칭·형식 오류는 기존 수집값을 지우지 않는다. 프로필 조회 자체가 실패하면 Crew 쓰기 전에 중단한다. 재동기화는 공개 여부·관리자 소개글·수정값을 덮어쓰지 않는다.

## 검증

```sh
npm ci
npm run prisma:generate
npm run typecheck
npm run build
npm run crew:academic:test
npm run admin:auth:smoke
npm run http:smoke
```

통합 테스트는 합성 데이터만 사용한다. 로컬 PostgreSQL에 별도 `ahp_crew_year_test` DB를 만들고 `DATABASE_URL`을 해당 DB로 설정한 뒤 아래를 실행한다. 테스트는 localhost/127.0.0.1의 이 DB 이름만 허용하며 자신이 만든 UUID 기반 레코드만 삭제한다.

```sh
npm run prisma:migrate:deploy
npm run crew:academic:integration
```

## 배포 순서와 승인 조건

1. 연결된 백엔드·프런트엔드 PR 모두 사용자 승인 및 main 병합을 확인한다. 승인 전 운영 변경은 하지 않는다. 실제 배포할 병합 SHA와 현재 운영 SHA를 기록한다.
2. 기존 배포 매니페스트, 이미지, DB 백업을 보존한다. 비밀값이나 원본 학번을 로그/PR에 출력하지 않는다. 배포 시점의 변경사항과 기존 로컬 호환 패치를 비교하고, 이번 승인 범위 밖 변경을 임의로 포함하지 않는다.
3. `CrewSource`/`CrewAdminProfile`의 현행 컬럼과 Prisma 마이그레이션 이력을 확인한다. 이 변경은 nullable TEXT 컬럼 4개를 추가할 뿐 기존 행을 수정/삭제하지 않는다.
4. 정상적인 마이그레이션 이력이 있는 DB에는 `prisma migrate deploy`를 사용한다. 기존 운영처럼 `prisma db push`로 만든 DB에는 전체 과거 마이그레이션을 무작정 실행하거나 이력을 일괄 조작하지 않는다. 스키마와 이력을 비교해 이번 additive SQL만 안전하게 적용하고, 적용 내역을 기록한다. 이미 동일 컬럼이 있거나 다른 변경과 충돌하면 먼저 검토한다.
5. 백엔드를 배포한 뒤 Crew를 재동기화한다. 연도 컬럼을 만드는 것만으로 기존 레코드가 채워지지는 않는다. 가능하면 `NotionContentSyncService.syncCrews()`만 호출해 다른 콘텐츠는 건드리지 않는다. `npm run admin:content:sync`와 콘솔 전체 동기화는 모든 콘텐츠를 수집하므로 이 차이를 인지하고 사용한다.
6. 프런트엔드를 배포하고 공개 API·홈페이지·크루북·상세·참여자 표시를 확인한다. 미매칭 건수, 정상 연도 건수, 관리자 수정값/공개 여부 보존 여부를 집계로 검증한다. 전체 학번은 공개하지 않는다.

## 롤백

문제가 있으면 이전 앱 이미지로 되돌리고, 추가한 nullable 컬럼과 새 수집값은 유지한다. **오래된 스키마의 `prisma db push` init container를 그대로 실행하면 새 컬럼을 제거하려 할 수 있으므로 롤백 전에 이를 차단한다.** `--accept-data-loss`, `migrate reset`, 컬럼 삭제는 사용하지 않는다. 배포 후 새 관리자 편집이 있을 수 있으므로 DB 백업 복구도 자동으로 수행하지 않는다.
